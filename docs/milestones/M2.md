## The simulation (PRD §7.10)

Three devices (Doctor and two Staff), each running the app's and the service worker's sync engines on one store with no shared lock. They run against the real API on an in-process SQLite D1 (`test/sim/sqliteD1.ts`: the local D1 proxy blocks on every statement and was too slow for 1,000 runs; the API's own tests still use it). The network goes online, offline and flaky: requests are dropped, responses are lost after the server applied them, and latency varies so responses overtake each other.

Checked at every step: pending changes are shown; no row steps back to an older version; no two active bookings overlap, and every clash names an existing winner. Checked after each run: outboxes empty; one `sync_ops` row and one audit row per op; every answer to a re-sent op equals the stored one; every device holds exactly the server's rows and the very same rows as the other devices, with none still marked "not sent yet".

**Mutation check** (break one thing, run 300 runs): no clash check on the server, rows stepping back to an older version, no replay of pending edits, and a refused create left on the device were **all caught**.

**Bug found by the simulation and fixed:** a row could stay marked "Not sent yet" for good when the service worker pulled it while its op was still waiting and the answer to the op came back later (`apps/pwa/src/lib/sync.ts`, unit test "clears 'not sent yet' …"). The sync review also found that pruning could let a late response bring back a dropped booking, and that old bookings changed on the server were announced as new. Both are fixed and unit-tested.

2. Turn on airplane mode. Book 3 patients. The pill shows "Offline since …" and the bookings show "Not sent yet".

## Known limits

- The device keeps bookings from today − 30 days; PRD §7.1's upper bound (today + 120 days) is not applied, so a first install also receives bookings further ahead (more data, never less).
- Older bookings load on demand later (patient history screen, a later milestone).
